Infraestrutura de rede corporativa: VLANs, roteamento e DHCP no Packet Tracer

Por Elias de Siqueira · 28 de outubro de 2026 · 7 min de leitura

  • redes
  • cisco
  • vlan
  • dhcp
  • packet-tracer

Neste laboratório, montei no Cisco Packet Tracer a rede de uma empresa fictícia com quatro setores. Cada setor ficou em uma VLAN própria, o roteamento entre elas ficou num switch multicamada e todos os computadores recebem IP de um único servidor DHCP. Aqui conto como configurei, como testei e os três problemas que apareceram no caminho.

O cenário

A empresa tem quatro setores: Administrativo, TI, Comercial e Servidores. Os requisitos eram:

  • Separar o tráfego de cada setor em uma VLAN e uma rede IP próprias.
  • Permitir a comunicação entre os setores por meio de roteamento no switch de núcleo.
  • Entregar endereços IP automaticamente aos computadores, a partir de um único servidor DHCP na rede de servidores.
  • Ligar os switches de acesso ao núcleo por trunks 802.1Q.

A topologia e o endereçamento

Usei uma arquitetura de duas camadas, com núcleo colapsado. O CORE, um Catalyst 3650, faz o papel de núcleo e de distribuição: nele ficam os gateways das quatro redes e o roteamento entre elas. Os switches SW1, SW2 e SW3, todos Catalyst 2960, formam a camada de acesso e se ligam ao CORE em estrela, cada um por um trunk.

O plano de endereçamento ficou assim:

Configuração passo a passo

1. VLANs em todos os switches

Criei e nomeei as quatro VLANs no CORE e nos três switches de acesso:

vlan 10
 name ADMINISTRATIVO
vlan 20
 name TI
vlan 30
 name COMERCIAL
vlan 40
 name SERVIDORES

2. Portas de acesso e trunks

No SW1 e no SW2, cada PC fica numa porta de acesso da VLAN do seu setor. No SW3, a porta do servidor fica na VLAN 40. A ligação de cada switch com o CORE é um trunk:

! SW1 e SW2
interface FastEthernet0/1
 switchport access vlan 10
 switchport mode access
interface FastEthernet0/2
 switchport access vlan 20
 switchport mode access
interface FastEthernet0/3
 switchport access vlan 30
 switchport mode access
interface GigabitEthernet0/1
 switchport mode trunk

No CORE, as portas Gi1/0/1, Gi1/0/2 e Gi1/0/3 também ficaram em trunk. Foi aqui que apareceu o primeiro problema, que conto mais abaixo.

3. Gateways e roteamento no CORE

Cada VLAN ganhou uma interface virtual (SVI) com o IP do gateway, e o ip routing liga o roteamento entre elas:

ip routing
!
interface Vlan10
 ip address 192.168.10.1 255.255.255.0
interface Vlan20
 ip address 192.168.20.1 255.255.255.0
interface Vlan30
 ip address 192.168.30.1 255.255.255.0
interface Vlan40
 ip address 172.16.40.1 255.255.255.0

4. DHCP centralizado com relay

O pedido DHCP do PC é um broadcast, e broadcast não sai da VLAN. Por isso configurei o ip helper-address nas SVIs das redes de usuários: o CORE recebe o pedido e encaminha ao servidor 172.16.40.2 em unicast, informando o próprio IP. O servidor usa esse endereço para escolher o pool da rede certa.

interface Vlan10
 ip helper-address 172.16.40.2
interface Vlan20
 ip helper-address 172.16.40.2
interface Vlan30
 ip helper-address 172.16.40.2

No servidor, criei um pool para cada rede de usuários, com o gateway da VLAN e o primeiro endereço no .100. O serverPool é o pool padrão do Packet Tracer e fica sem uso, porque a VLAN 40 só tem o servidor.

Um detalhe que vale observar é o TTL. Na mesma VLAN, a resposta chega com TTL 128, porque o pacote não passa por roteamento. Para outra VLAN e para o servidor, chega com 127: o CORE roteou o pacote e descontou um salto. E o primeiro pacote perdido no ping entre VLANs é esperado, porque ele se perde enquanto o CORE resolve o ARP do destino.

Problemas e soluções

Problema 1: trunk recusado no CORE

Os PCs da mesma VLAN em switches diferentes não se comunicavam. Ao configurar o trunk na Gi1/0/1 do CORE, o switchport mode trunk retornava % Invalid input detected.

A solução foi executar switchport na interface, colocando a porta em camada 2, e só então configurar o trunk. Como isso resolveu, a porta provavelmente estava operando em camada 3.

Lição: em switch multicamada, vale conferir se a porta está em camada 2 antes de configurar trunk. O show interfaces gi1/0/1 switchport mostra isso.

Problema 2: PCs sem comunicação até renovar o DHCP

Com tudo configurado, a comunicação a partir dos PCs do SW1 parecia falhar, como se as VLANs não passassem pelo trunk. No CORE, o show vlan brief e o show interfaces trunk mostravam tudo certo, e com IP fixo todos os pings funcionaram. Ou seja, o problema estava no endereçamento dos PCs.

Quando refiz o pedido DHCP, os PCs receberam IP sem nenhuma outra mudança na rede. A causa provável: os pedidos anteriores foram feitos antes de a rede estar completa, e o PC não repete o pedido sozinho.

Lição: depois de mexer na rede, renovar o IP antes de concluir que há falha, e testar com IP fixo para separar problema de rede de problema de DHCP.

Problema 3: configuração com sobras

Esse não parava a rede: apareceu na revisão do running-config, antes de publicar. Algumas SVIs tinham ip helper-address apontando para os próprios gateways do CORE, além do servidor, e as portas trunk tinham linhas switchport access vlan que sobraram de configurações anteriores.

Deixei só o helper para o servidor, removi as sobras com no switchport access vlan e salvei a configuração limpa com copy running-config startup-config.

Lição: o ip helper-address aponta para o servidor DHCP, e cada correção precisa ser salva para sobreviver a um reinício.

O que aprendi e próximos passos

  • Tráfego na mesma VLAN é de camada 2: passa pelos trunks e não depende do gateway.
  • Em switch multicamada, a porta precisa estar em camada 2 para virar trunk.
  • O relay DHCP aponta para o servidor, que escolhe o pool pela rede da SVI que encaminhou o pedido.
  • Testar com IP fixo separa falhas de rede de falhas de DHCP.
  • Revisar e salvar a configuração antes de documentar.

Na versão 2, vou evoluir este mesmo laboratório com redundância do CORE. Depois disso, ficam na lista ACLs para controlar o acesso entre os setores e um roteador de borda para simular a saída para a internet.
